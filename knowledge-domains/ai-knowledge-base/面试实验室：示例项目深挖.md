# 面试实验室：示例项目深挖

本章收录面试实验室的完整问答，保留题号与英文问题。实现细节来自独立的学习示例项目，不代表现有小程序已部署这些功能，也不代表读者已有相关经历；面试回答应替换为自己的真实实践。

## I1 · 为什么不用框架？

英文问题：Why no framework?

为了理解并掌控循环的每个部分：校验、预算、审批、幂等。框架会把这些藏起来。代价是 checkpoint 和恢复要自己做。之后我又用 LangGraph 重建了同一个用例（Lab 12），所以能准确说出框架提供了什么（图、checkpoint、暂停/恢复、重试策略），以及没提供什么（身份、幂等、审批规则）。

## I2 · 为什么幂等键是 `hash(run_id + args)`？

英文问题：Why is the idempotency key `hash(run_id + args)`?

它是确定性的：同一个 run 中相同的提议动作总是得到相同的 key，所以重复审批或重试会在数据库层去重。缺点是：同一个 run 中有意创建两个完全相同的动作会被合并成一个；加入步骤 ID 或意图 ID 可以解决。

## I3 · 为什么审批人不能修改参数？

英文问题：Why can't the approver change arguments?

审批必须对应所审阅的确切内容。修改后的参数是一个新动作，需要重新校验并生成新的幂等键；否则同一个 key 可能对应不同的内容。

## I4 · 模型给出无效动作时会发生什么？

英文问题：What happens on an invalid model action?

这一步被标记为 invalid_action，并把一个错误观察（只包含错误类型）反馈给模型，让它自我纠正。这一步仍计入 max_steps，所以垃圾输出不会无限循环。

## I5 · 为什么 `search_knowledge` 不生成答案？

英文问题：Why doesn't `search_knowledge` generate an answer?

它只做检索，这样就不会有超出 Agent token 预算的隐藏 LLM 调用；由 Agent 负责综合答案。命中内容也被截断到 800 字符以控制上下文大小。

## I6 · 为什么 `calculate` 要解析 AST？

英文问题：Why does `calculate` parse an AST?

对模型输出使用 eval 等于远程代码执行。AST 遍历只允许数字常量、一元 ± 和 + - * / %，限制节点数量和数值大小，并拒绝 inf 和 NaN。

## I7 · `required_tools` 是怎么工作的？

英文问题：How does `required_tools` work?

在必需工具完成之前，动作 schema 中 tool 的 enum 被收窄为下一个必需工具，生成后还会再检查一次。所以模型必须使用该工具，但参数仍由它来写。在 native 模式下，则是只提供那个工具。

## I8 · 要上生产，你会改什么？

英文问题：What would you change for production?

用带租约的队列 worker 替代进程内的锁；自动的恢复清扫器；恢复时重新解析请求人的权限；用真实 tokenizer 和厂商上报的用量做预算；把图的 events 导出到 OpenTelemetry；按租户配额；MCP server 使用 OAuth；用评估套件挑选更强的工具调用模型；外部写工具要有服务商侧幂等和补偿。

## I9 · 讲讲 follow-up 刚写入后进程就挂掉时会发生什么。

英文问题：Walk me through what happens when the process dies right after the follow-up is written

execute 节点插入了那一行，然后进程在 LangGraph 保存该节点的 checkpoint 之前就死了。重启后 run 的 next 仍是 ["execute"]，所以视图显示 interrupted。POST /resume 以请求人的身份重新运行 execute：它先在账本中查找幂等键，找到那一行，就把它作为回执返回（reused_existing: true），而不再插入。scripts/lab12_crash_demo.py 用真实的 os._exit(137) 演示了这一过程。

## I10 · 为什么即使由审批人恢复，Lab 12 的节点也以请求人的身份运行？

英文问题：Why do the Lab 12 nodes run as the requester, even when an approver resumes the run?

Agent 代表提出请求的人行事。如果节点以点击“批准”或“恢复”的人的身份运行，一个权限更大的审批人就可能意外扩大 Agent 能检索或写入的范围。所以 run 注册表保存请求人的身份，每次图调用都在 acting_as(requester) 中运行；审批人的身份单独记录在审批决定里。生产中我会重新解析请求人当前的权限，而不是信任保存的快照。

## I11 · 你的 verify 节点检查什么？为什么用代码而不是再调用一次 LLM？

英文问题：What does your verify node check, and why is it code rather than another LLM call?

确定性 verify 节点可以检查证据 ID 是否有效、写动作是否获得授权、参数是否与审批内容一致，以及外发地址是否在允许范围。但“目标是否真的要求该动作”不总能用关键词完整判定，拦截邮箱和链接也无法覆盖所有外泄方式。明确任务意图应来自受信 UI 或结构化请求，高影响写入仍需审批；代码校验与人工复核共同覆盖语义边界，不能声称确定性程序天然无法被骗。

## I12 · 你的 MCP server 是如何保证安全的？

英文问题：How is your MCP server secured?

示例 MCP server 只暴露只读搜索，输入限制长度与 top_k，并通过 Knowledge API 执行权限与文档状态检查。只读限制应落实在底层凭据和服务接口，不只依赖工具注解。单用户本地部署可以使用该用户的受限凭据；多用户服务必须建立每次请求的身份与权限，不可共享启动者的 token。按协议实现授权与面向正确受众的令牌，不盲目透传客户端 token，也不把 token 交换当作所有部署的固定要求。

## I13 · 你的评估套件告诉了你旧的 5 个 golden task 没告诉你的什么？

英文问题：What does your evaluation suite tell you that the old five golden tasks didn't?

可靠性和安全性。每个任务运行多次，所以能同时看到 pass@1 和 pass^k，不稳定的任务会暴露出来，而不是一次幸运的演示。它包含对抗性任务：含提示注入的文档、计算器里的代码、预算和步数限制。它把“模型提议了坏动作”（质量失败）与“没有审批就写入了坏东西”（安全失败，必须为 0，否则整个运行失败）区分开。比较 _required 和 _autonomous 两个变体，能为“workflow 优先”提供数据。
