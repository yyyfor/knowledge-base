# RAG 平台架构与数据职责

RAG 平台是把文档、检索、模型和权限连接起来的知识问答系统。它不是“向量数据库加聊天接口”：必须知道每份数据由谁负责、如何更新、怎样证明回答引用的是用户有权查看的当前资料。

## 入门：五类数据各自做什么

PostgreSQL 是关系数据库，用事务保存文档身份、版本、权限、处理状态和审计记录。原始文件通常放在对象存储或受管理的文件系统中；关系表保存文件引用与哈希。权威数据（Source of Truth）是发生冲突时用于判定事实的数据，不是哪个数据库查询最快。

Elasticsearch 保存关键词倒排索引，适合编号、产品名和精确词语。Qdrant 或 pgvector 保存向量索引，适合语义改写后的问题。Redis 可保存可失效的缓存。图存储保存实体关系，例如文档引用关系；没有图查询需求时，不必为了凑齐架构引入它。

索引是原文的派生数据（Derived Data），应能从受版本管理的原文、解析结果和配置重建。Agent 检查点保存审批与运行进度，也可能是不可重建的状态，不能因为存在 PostgreSQL 就忽略检查点库和原始文件的备份。

## 进阶：走完一次问答

用户提交问题 → 服务端认证并确定权限 → 关键词和向量检索 → 融合与重排 → 权威库核验候选 → 组装证据 → 模型生成 → 校验引用 → 返回答案和来源。这里每个箭头都是可测量的步骤，检索服务故障不能被伪装成“资料中没有答案”。

以“某功能支持哪些配置”为例，关键词命中配置名，向量检索命中表达方式不同的说明。模型只能根据核验后的片段回答；响应保存文档版本、章节标识和引用文本，用户可直接回到原文，而不是只看到一个无法核对的结论。

## 项目实践：从单进程开始

来源架构采用一个 FastAPI 进程连接多个存储，这是一种开发快、部署简单的起点，不是要求每个模块都拆成微服务。本小程序当前使用确定性的本地知识检索，并没有部署这些 RAG 组件；这里的方案用于扩展练习。

练习先只使用 PostgreSQL 加原文存储，完成上传、搜索和带引用的回答。测量查询集上的质量、延迟、数据量和运维成本后，再决定是否增加专用向量库或独立工作者。记录每个组件的输入、输出、所有者、备份方式和重建步骤。

## 高阶：明确启用条件与降级

来源项目中的 RAG、图查询和安全开关属于某次开发快照，不是生产默认建议。生产请求必须先完成认证授权；安全未启用时只能在隔离的本地环境使用。模型不可用时可降级为关键词搜索和原文阅读，但页面要明确当前没有生成答案。

验收时分别删除可重建索引、关闭模型服务、撤销文档权限、恢复备份。确认重建后的文档版本一致，故障有明确状态，用户不会获得旧权限下的证据。持久化数据库多于一个时，备份与恢复也必须覆盖它们之间的版本关系。
