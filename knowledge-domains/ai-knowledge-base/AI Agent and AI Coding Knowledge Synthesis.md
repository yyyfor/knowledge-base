Agent 和 AI Coding 的核心不是“让模型多做事”，而是用控制流、上下文、工具、验证、安全边界和可复用 Skills，把零散的大模型能力组织成可长期使用的工程与个人生产力系统。

## 适用层级

- Level 1 Beginner：理解 Agent、Workflow、AI Coding、Skills、Context Engineering 的基本概念和使用边界。
- Level 2 Intermediate：能把 AI 工具用于真实工作流，设计任务拆解、工具调用、验证流程和安全边界。
- Level 3 Advanced：能设计生产级 Agent 或团队级 AI Coding 规范，关注评估、Tracing、权限、恢复、治理和成本。

## 一句话总结

Agent 是动态决策系统，AI Coding 是人机协作工作流；两者真正可用的前提，都是把模型能力放进可控、可验证、可复用的工程框架里。

## 核心结论

Agent 的本质不是单次模型调用，而是模型在循环中持续感知、决策、调用工具并根据反馈调整行动。Workflow 与 Agent 的关键区别是控制权：Workflow 由代码预设路径，Agent 由模型根据上下文动态决定下一步。AI Coding 对非技术人员也有价值，但前提是任务足够清晰、上下文足够完整、步骤足够小，并且每一步都有验证办法。生产级使用不能只依赖 prompt，需要 Context Engineering、Skills、Harness、Eval、Tracing、安全边界和恢复机制共同支撑。

## 核心概念

- Agent Loop：模型调用、工具选择、工具执行、结果回传和继续决策组成的循环。
- Workflow：由代码或配置预设步骤的确定性流程，适合路径明确、验证标准稳定的任务。
- Context Engineering：决定哪些信息进入模型、何时进入、如何压缩、如何排序和如何保留的工程能力。
- Tool Use：模型通过结构化接口调用外部工具、数据源或系统动作。
- Skills：把重复任务封装成带触发条件、步骤、约束和输出格式的可复用能力。
- Harness：模型外层的工程系统，包括上下文构造、工具路由、状态管理、策略约束、评估和观测。
- AI Coding：用 AI 协助代码、脚本、文档、原型、数据处理和自动化任务的人机协作方式。

## 为什么重要

AI 工具的门槛正在降低，但失败成本并没有消失。没有控制流的 Agent 容易失控，没有上下文治理的 AI Coding 容易跑偏，没有验证和安全边界的自动化容易产生错误操作。对个人来说，这套方法能把 AI 从“聊天工具”升级成“工作流助手”；对团队来说，它能把一次性的 AI 经验沉淀为标准流程、技能库和质量控制体系。

## 关键点

- Agent 适合开放目标和动态决策，Workflow 适合确定步骤和稳定流程。
- Agent Loop 至少要包含目标、上下文、工具、状态、停止条件、预算限制和失败处理。
- 长上下文不是越长越好，关键是筛选、压缩、去重、引用和优先级。
- 工具越多不一定越强，工具 schema、权限、错误处理和返回结构会直接影响可靠性。
- Skills 的核心是触发条件和边界，不是泛泛介绍“这个技能能做什么”。
- AI Coding 最适合从小任务开始：明确目标、提供上下文、先计划、再执行、再验证。
- 截图、样例文件、项目规则和验收标准，通常比抽象描述更能帮助 AI 正确工作。
- 生产级 AI 应用必须关注评估、Tracing、权限、审计、回退和安全。

## 基础例子

一个产品经理想让 AI 帮忙生成需求原型。低质量做法是直接说“帮我做个页面”。更好的做法是提供目标用户、业务流程、截图参考、字段说明、限制条件和验收标准，然后让 AI 先输出计划，再生成原型，最后逐项检查交互、异常状态和文案是否符合预期。

一个工程团队想做企业知识库问答。普通 LLM 调用只能回答当前上下文里的内容；更完整的方案需要文档解析、chunk、embedding、检索、rerank、引用生成、权限过滤、反馈收集和离线评估。这个系统已经不只是 prompt，而是一套 RAG 与 Agent Harness。

## 适用场景

- 个人工作流：用 AI 整理网页、生成会议纪要、写脚本、做原型、检查 PRD、总结行业研究。
- 团队协作：把常见任务沉淀成 Skills，例如 PRD Review、事故排查、周报生成、竞品分析和上线检查。
- 工程系统：设计 Agent 时先决定控制模式，再设计上下文、工具、状态、验证和安全策略。
- 培训分享：把 Agent 工程文章转成演示材料时，应补充讲稿、案例、练习题和 checklist。
- 面试准备：回答 AI Agent 或 AI Coding 问题时，应讲清业务目标、系统边界、数据流、工具调用、失败模式和治理方式。

## 典型流程

### Agent 工程设计流程

- 判断任务类型：确定性流程用 Workflow，开放目标和动态路径才考虑 Agent。
- 设计控制模式：选择链式、路由、并行、编排者-执行者或评估优化模式。
- 设计上下文：区分系统规则、项目知识、用户目标、运行时状态、检索材料和历史记忆。
- 设计工具：限制工具数量，明确输入 schema、权限、timeout、retry、错误返回和审计日志。
- 设计验证：建立测试集、自动校验、人工确认、回退机制和质量指标。
- 设计安全：高风险动作需要审批、最小权限、沙箱、日志和可撤销操作。
- 设计恢复：长任务要持久化进度，支持暂停、恢复、重试和回滚。

### 非技术人员 AI Coding 工作流

- 明确目标：说明要解决什么问题、目标产物是什么、成功标准是什么。
- 提供上下文：补充截图、文件、样例、项目规则、约束和已有风格。
- 拆小任务：每次只处理一个可验证目标。
- 先要计划：复杂任务先让 AI 输出步骤、风险和预计改动。
- 执行与验证：每一步检查结果，必要时回滚或调整。
- 沉淀 Skills：把重复任务写成触发条件、操作步骤、输出格式和检查清单。
- 设置边界：生产环境、密钥、支付、用户数据等高风险内容必须谨慎处理。
- 定期复盘：把有效提示、失败案例和最佳实践更新到知识库。

## 关键公式或模型

Agent 可用性 = 任务边界清晰度 x 上下文质量 x 工具可靠性 x 验证强度 x 安全约束 x 恢复能力

AI Coding 任务质量 = 目标清晰度 x 上下文完整度 x 任务粒度 x 验收标准 x 用户验证能力

这两个模型不是数学公式，而是实务检查框架。任一项过低，Agent 或 AI Coding 都可能从“智能助手”退化成“不可控自动化”。

## 常见误区

- 误区：Agent 就是更长的 prompt。实际 Agent 需要 loop、tools、state、policy、memory 和 validation。
- 误区：工具越多 Agent 越强。工具过多会增加上下文成本、选择错误和权限风险。
- 误区：上下文越长越好。长上下文会带来噪音、成本、延迟和注意力稀释。
- 误区：非技术人员不能用 AI Coding。真正门槛不是写代码，而是把任务讲清楚并能验证结果。
- 误区：AI 生成的代码能跑就可以上线。上线前仍需要安全检查、测试、权限审查和异常处理。
- 误区：演示页可以直接当知识库正文。演示材料更适合传播，进入知识库时需要补充上下文、结构和引用。

## 风险点

- 权限风险：Agent 调用工具时可能访问或修改不该操作的数据。
- 安全风险：不要把密钥、生产凭证、敏感客户数据直接交给 AI。
- 质量风险：模型可能生成看似合理但事实错误或逻辑不完整的结果。
- 成本风险：长上下文、多工具和多轮循环会显著增加 token、延迟和调用费用。
- 可观测性风险：如果没有 Tracing，很难复盘模型为什么做出某个决策。
- 维护风险：Skills、工具 schema、项目规则和产品功能会变化，需要定期更新。

## 进阶内容

### Agent 控制模式

- Prompt Chaining：把复杂任务拆成顺序步骤，适合明确流程。
- Routing：根据输入类型分发到不同路径，适合分类和多场景处理。
- Parallelization：多个子任务并行处理，适合可拆分任务。
- Orchestrator-Workers：一个主 Agent 负责任务分派，多个 worker 执行具体任务。
- Evaluator-Optimizer：一个执行者生成结果，另一个评估并提出优化，适合质量要求高的任务。

### Context Engineering 分层

- 固定规则：身份、权限、输出格式和项目约束。
- 项目知识：代码结构、业务术语、团队规范和长期背景。
- 运行时上下文：当前任务、用户输入、文件、截图、工具结果。
- 记忆：用户偏好、历史决策、长期稳定事实。
- 压缩层：摘要、引用、关键决策、待办和恢复点。

### Skills 设计原则

- 描述触发条件，而不是只描述能力。
- 一个 Skill 只解决一类任务。
- 写清楚适用场景和不适用场景。
- 提供输入要求、执行步骤、输出格式和验收标准。
- 保留反例，避免错误触发。

## 案例

### 案例 1：把网页整理成知识库条目

输入是三篇网页，目标不是复述文章，而是沉淀为可检索、可引用、可复用的知识页面。正确流程是先判断来源可信度，再提炼核心结论和关键知识点，之后重组为背景、问题、分析、结论和行动建议，最后补充标签、相关链接和一句话知识卡片。

### 案例 2：企业内部 AI 助手

企业想让 AI 帮员工查询制度和项目文档。如果只把文档塞进 prompt，无法解决权限、版本、引用、召回和审计问题。更好的方案是 RAG 加 Agent Harness：文档入库、权限过滤、检索、rerank、引用生成、反馈收集、质量评估和管理后台共同工作。

### 案例 3：产品经理用 AI Coding 做原型

产品经理提供需求说明、截图参考、页面字段和验收标准，让 AI 先输出计划，再生成页面原型。完成后检查移动端展示、异常状态、输入框行为、颜色一致性和交互路径。这个过程的重点不是“AI 会不会写代码”，而是人能否给出清晰上下文并验证结果。

## Checklist

- 是否先判断任务应该用 Workflow 还是 Agent？
- 是否明确目标、边界、停止条件和验收标准？
- 是否区分系统规则、项目上下文、运行时信息和长期记忆？
- 是否限制工具权限，并定义 timeout、retry、error handling 和 audit log？
- 是否有自动或人工验证结果的方法？
- 是否记录模型输入、工具调用、响应、成本、延迟和失败原因？
- 是否避免把密钥、生产凭证和敏感数据交给 AI？
- 是否把重复任务沉淀为 Skills 或模板？
- 是否为长任务设计进度持久化、恢复和回滚？
- 是否定期更新工具能力、产品功能和来源信息？

## 结构化摘要

背景：大模型和 AI Coding 工具降低了智能自动化门槛，Agent 和非技术人员 AI Coding 逐渐成为真实工作方式的一部分。

问题：很多使用方式仍停留在 prompt 层，缺少任务拆解、上下文治理、工具边界、质量验证和安全机制，导致结果不可控、不可复用、不可审计。

分析：Agent 需要围绕控制流、上下文、工具、记忆、评估、Tracing 和安全边界进行系统设计；AI Coding 需要围绕目标、上下文、任务粒度、计划、验证和 Skills 沉淀形成稳定工作流。

结论：模型能力只是基础，真正的生产力来自把模型接入可控流程，并持续沉淀为知识库、Skills、模板和检查清单。

行动建议：个人从小任务开始，团队从高频重复流程开始，工程系统从权限和验证开始；所有 AI 工作流都应保留来源、过程、结果和复盘入口。

## 可复用框架 / 方法论

### AI 能力落地四层框架

- 使用层：个人用 AI 完成整理、写作、代码、原型和分析。
- 流程层：把任务拆成计划、执行、验证和复盘。
- 能力层：沉淀 Skills、模板、工具接口和项目规则。
- 治理层：加入权限、安全、评估、Tracing、审计和版本管理。

### 技术文章进入知识库的整理框架

- 来源判断：作者、时间、链接、领域、可信度。
- 观点提炼：先写结论，再补背景。
- 知识拆解：概念、逻辑、场景、误区、风险、案例、Checklist。
- 结构重组：背景、问题、分析、结论、行动建议。
- 可复用化：提炼方法论、模板、标签和相关知识链接。
- 维护机制：标注需更新的信息，例如工具功能、产品能力、价格、模型上下文和 API 行为。
