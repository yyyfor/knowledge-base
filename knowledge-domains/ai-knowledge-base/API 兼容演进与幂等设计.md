# API 兼容演进与幂等设计

API 兼容性是旧客户端在服务升级后仍能按照原契约正确使用接口。字段存在还不够：类型、枚举、默认行为、校验、排序和错误语义都可能构成契约。

## 入门：什么是破坏性变更

删除字段、改变类型、增加必填请求参数、收紧旧输入校验和改变默认排序都可能破坏客户端。新增响应字段通常更容易兼容，但严格解析器仍可能拒绝未知字段。新增枚举值也可能让旧客户端的分支处理失败。

OpenAPI 描述接口形状，Consumer-Driven Contract Testing（消费者驱动契约测试）由客户端表达它依赖的行为，并由服务端验证。静态接口差异检查与运行时契约测试互相补充，都不能替代业务语义测试。

## 进阶：Expand-Contract 四步

Expand（扩展）先新增字段，保留旧字段；Migrate（迁移）回填数据并迁移调用方；Verify（验证）确认旧读写路径不再使用；Contract（收缩）才删除旧字段。双写需定义谁是权威值、发生冲突时如何处理，不能只是多写一个列。

例如把 description 迁移为 content，后端先同时接受旧字段和新字段，明确同时提交时的规则；旧版小程序继续工作。部署新前端后观察旧请求使用情况，达到公告的退役条件后才移除旧契约。修改提醒接口时同样应先兼容已有记录与旧客户端。

## 项目实践：安全重试创建

创建请求携带 Idempotency-Key 或 clientRequestId。服务端以用户与操作范围建立唯一约束，存请求摘要、执行状态和结果。相同键相同参数返回已保存结果，相同键不同参数返回冲突；在执行中的请求不能被当作已经成功。

本小程序行动创建已有 clientRequestId 去重，是现有实践，不是新增 AI 功能。进一步练习并发发送同一请求、提交后丢失响应、服务重启后重试，验证只产生一项行动。幂等键保留期限与重试窗口要有明确约定。

## 高阶：分页、错误与版本

游标分页使用稳定排序和唯一平局键，例如 createdAt 加 id，减少大 offset 扫描。数据边读边变仍可能导致视图变化；需要快照一致性时另行设计版本或快照，不能宣称游标天然不会漏项。

错误可采用 RFC 9457 的 Problem Details，机器依赖稳定类型或代码，不依赖中文提示文本。新版本用于确实无法维持的语义变化，旧版本设退役计划。上线验证同时运行旧请求样本、契约测试和权限测试，再确认回滚后的旧服务仍能读取新数据。
