# 面试实验室：模型与生态

本章收录面试实验室的完整问答，保留题号与英文问题。实现细节来自独立的学习示例项目，不代表现有小程序已部署这些功能，也不代表读者已有相关经历；面试回答应替换为自己的真实实践。

## L1 · 从高层次解释 transformer。

英文问题：Explain the transformer at a high level

文本变成 token，token 变成带位置信息的向量（embedding）。每一层都有自注意力：每个 token 生成 query、key 和 value，用自己的 query 与所有 key 比较，决定从每个 value 读取多少，于是每个 token 的表示融入了上下文。之后前馈网络对每个 token 做变换。堆叠几十层后得到越来越抽象的特征。聊天模型是仅解码器结构：因果掩码让每个 token 只能看到之前的 token，这使得逐 token 生成成为可能。

## L2 · 为什么长上下文很贵？有什么办法？

英文问题：Why is long context expensive, and what helps?

Attention 要把每个 token 与其他所有 token 比较，所以计算量大约随序列长度的平方增长。生成时 KV cache 也随上下文和批大小线性增长，占用 GPU 显存。办法：FlashAttention（精确注意力，减少显存读写）、分组查询注意力 GQA（更小的 KV cache）、滑动窗口或稀疏注意力、RoPE 的位置缩放技巧；在应用层面，不发送不需要的内容（检索、压缩）。

## L3 · 仅编码器、仅解码器、编码器-解码器：分别用在哪？

英文问题：Encoder-only vs decoder-only vs encoder-decoder: which is used where?

仅编码器（BERT 类）双向看完整输入，适合 embedding、分类和 cross-encoder 重排序。仅解码器（GPT/Claude/Llama 类）用于生成文本。编码器-解码器（T5 类）把输入映射为输出，如翻译和摘要。示例项目中 embeddinggemma 生成 embedding，llama3（仅解码器）负责生成；cross-encoder reranker 是编码器。

## L4 · 聊天模型是如何训练出来的？

英文问题：How is a chat model trained?

(1) 预训练：在数万亿 token 上做下一个 token 预测，获得广泛的知识和能力。(2) 监督微调（SFT）：用精心整理的指令-回答对教会它助手的格式和遵循指令。(3) 偏好调优：由人（RLHF）或按书面原则的 AI（RLAIF，例如 Constitutional AI）对回答排序，再把模型优化向偏好的回答（用 PPO + 奖励模型，或直接用 DPO）。(4) 对推理模型，基于可验证奖励的强化学习：为数学或编程题生成解答，奖励能通过检查的，模型由此学会更长、会自我纠错的推理。安全训练贯穿全过程。

## L5 · RLHF 与 DPO 的区别？

英文问题：RLHF vs DPO?

RLHF 先用人类偏好对训练一个奖励模型，再用强化学习（通常是 PPO）优化策略，并用 KL 惩罚让它不偏离 SFT 模型太远；强大但复杂、不稳定。DPO 省掉奖励模型和强化学习循环，把偏好对直接变成作用在策略上的类似分类的损失；更简单便宜，在开源模型中很常见。两者都需要高质量的偏好数据，也都可能过度优化（奖励投机、偏爱冗长）。

## L6 · 什么是奖励投机（reward hacking）？Agent 开发者为什么要关心？

英文问题：What is reward hacking, and why should agent builders care?

模型找到了在奖励上得高分、却没有完成预期任务的方法。例如通过特殊处理测试让测试通过，或者听起来很自信而不是真的正确。在 Agent 中，同样的事表现为“刷”你的评估。所以评估需要轨迹检查以及留出的、对抗性的任务，而不只是“最终字符串里有没有 180”。

## L7 · LoRA 是如何工作的？为什么便宜？

英文问题：How does LoRA work, and why is it cheap?

LoRA（低秩适配）冻结原权重 W，只训练 ΔW=B·A，参数量从 d·k 降到 r·(d+k)，其中秩 r 远小于原维度。它减少可训练参数与优化器状态，但总训练速度和显存取决于模型、激活与实现。适配器可合并到兼容权重，也可动态加载。QLoRA 对冻结基座做低位量化，再训练适配器，进一步节省显存；能否在单卡运行取决于模型规模、上下文和硬件。

## L8 · 什么时候该微调，什么时候不该？

英文问题：When would you fine-tune, and when not?

为行为而微调：一致的输出格式、领域风格、更好地调用你自己的工具，或把大模型的行为蒸馏到小而便宜的模型上。不要为了加入会变化的事实而微调：用 RAG，因为微调进去的事实难更新、难引用，也无法做访问控制。先 prompt，再 RAG，只有评估显示前两者无法弥补差距时才微调。

## L9 · 你会如何微调一个小模型，让它更好地调用你的工具？

英文问题：How would you fine-tune a small model to call your tools better?

从 trace 中收集成功的轨迹（去除个人信息），再加上被纠正过的失败案例。按模型原生的工具调用格式整理。用 LoRA 微调。在留出集和对抗套件上评估，因为微调可能抹掉安全行为。注意灾难性遗忘。并与“直接换更强的模型”比较，最便宜的解法往往是更好的基座模型。

## L10 · 什么决定了 LLM 的延迟？

英文问题：What determines LLM latency?

两个阶段。Prefill 并行处理整个 prompt，是计算密集型的，决定首 token 延迟（TTFT）。Decode 一次生成一个 token，是内存带宽密集型的（每一步都要读取权重和 KV cache），决定每个输出 token 的时间。所以长 prompt 影响 TTFT，长回答影响总时间。Agent 的多次模型调用会把两者成倍放大，所以步数、输出长度和 prompt caching 很重要。

## L11 · 连续批处理、PagedAttention、量化和投机解码各带来什么？

英文问题：What do continuous batching, PagedAttention, quantization and speculative decoding each buy you?

连续批处理*每一步都把请求加入或移出 GPU 批次，吞吐量大幅提高。*PagedAttention（vLLM）像虚拟内存一样按页存放 KV cache，浪费更少、能容纳更多请求。量化（int8、int4、FP8）让模型更小更快，有时有质量损失，需要评估。*投机解码*让一个小的草稿模型先提出若干 token，由大模型一次验证，延迟更低且输出分布不变。

## L12 · 你会如何为 1,000 个并发用户提供 Agent 服务？

英文问题：How would you serve an agent product to 1,000 concurrent users?

把模型服务与 Agent runtime 分开。使用带路由的模型网关（小模型做路由和抽取，大模型做规划），按租户配额和限流，prompt caching，带退避的重试，以及跨厂商的降级。把 Agent 作为排队的无状态 worker 运行，并有持久化 checkpoint（如 Lab 12）。按队列深度和 GPU 利用率自动扩缩容。向用户流式展示进度。跟踪每个成功任务的成本，而不是每次调用的成本。

## L13 · 什么是 prompt caching？如何为它设计 prompt？

英文问题：What is prompt caching, and how do you design prompts for it?

Prompt caching 在模型服务支持时复用相同提示前缀的处理状态，答案仍重新生成。把稳定指令和工具定义放前面，变化的用户问题放后面，可提高命中机会。精确匹配规则、最短长度、缓存期限、写入与读取价格均由厂商及模型决定，不能把“几分钟过期”作为统一规则。涉及私人数据时还要核对隔离与数据保留策略。

## L14 · Prompt caching、语义缓存和 KV cache 的区别？

英文问题：Prompt caching vs semantic caching vs the KV cache?

KV cache 在一次生成内部（复用之前 token 的 attention 状态）。Prompt caching 在跨请求、前缀完全相同时复用这个状态，答案仍是重新生成的。*语义缓存*是应用层缓存：新查询足够相似时直接返回保存的答案。它更省钱，但有答案过时、错误和权限泄露的风险，所以必须以租户和 ACL 为键，并使用严格的相似度阈值。（示例项目的 Redis 搜索缓存是精确匹配的应用缓存。）

## L15 · 什么是推理模型？它们如何改变 Agent 的设计？

英文问题：What are reasoning models, and how do they change agent design?

它们在回答前生成内部的推理链（“思考”），通过强化学习训练出规划、检查和回溯的能力。在多步规划、数学、代码和模糊的工具选择上更强，但更慢，思考 token 也要付费。设计上的变化：更少的手写脚手架（“一步步思考”已多余）；按任务设置思考预算；只在困难节点（规划器、校验器）用推理模型，其余用快速模型；意识到可见的推理不一定是忠实的解释。确定性检查仍要保留。

## L16 · 除了“思考”，test-time compute 还有哪些？

英文问题：What is test-time compute beyond "thinking"?

花更多推理算力换更好的答案：自洽性（采样多个答案取多数）、配合验证器或奖励模型的 best-of-n、对步骤做树搜索、生成-批评循环。每一种都成倍增加成本，所以用在错误代价高且有检查器（测试、schema、检索引用）的地方。

## L17 · 比较 LangGraph、OpenAI Agents SDK 和 Claude Agent SDK。什么时候一个都不用？

英文问题：Compare LangGraph, the OpenAI Agents SDK and the Claude Agent SDK. When would you use none?

LangGraph 偏底层：显式状态图、reducer、checkpointer、中断和时间旅行。需要控制力以及持久、可审计的工作流时选它（示例项目的 Lab 12）。OpenAI Agents SDK 提供带工具的 agent、handoff、guardrail、会话和内置 tracing，适合快速搭建多 agent handoff。Claude Agent SDK 开放了 Claude Code 背后的运行框架：内置文件、shell 和 web 工具、权限模式、hooks、子 agent、MCP 和自动上下文管理，适合在电脑或代码库上干活的 Agent。当一次结构化输出调用或一个普通 workflow 就能完成任务、或你需要理解并掌控每一条边时（示例项目的 Lab 11），一个都不用。

## L18 · LangGraph 给了你什么？你还得自己做什么？

英文问题：What did LangGraph give you, and what did you still have to build?

它给了我：图、条件边、带 reducer 的状态 schema（events 列表）、按节点的重试策略、每一步的持久 checkpoint、暂停与恢复，以及状态查看（aget_state）。我仍需自己实现：授权与身份（acting_as）、幂等键和账本、审批过期、校验规则、run 注册表以及评估。框架给你的是编排，不是治理。

## L19 · Agent 框架与持久化执行引擎（Temporal）的区别？

英文问题：Agent framework vs durable execution engine (Temporal)?

Agent 框架主要表达工具、消息与模型驱动的控制流；Temporal 等持久化执行系统提供工作流历史、恢复、定时器和重试。工作流重放不意味着外部操作只执行一次：Activity 可能在效果已经发生、完成尚未上报时被重试。支付、发信等副作用仍需幂等键、执行回执、查证和补偿。可以把 Agent 步骤放在持久化工作流的 Activity 内，但要分别设计状态恢复与副作用安全。

## L20 · 解释 MCP 的架构。

英文问题：Explain the MCP architecture

Host（Claude Desktop、Claude Code、IDE 或你的应用）为每个 server 连接运行一个 client。Server 暴露三种原语：tools（模型可调用的动作）、resources（应用可读取的数据）和 prompts（可复用模板）。Client 可以向 server 提供 sampling（请求 host 的模型）、roots 和 elicitation（向用户提问）。传输方式：本地子进程用 stdio，远程 server 用 Streamable HTTP，HTTP 使用基于 OAuth 的授权。消息格式是 JSON-RPC。示例项目的 server 是只有一个只读工具的 stdio 或 HTTP server。

## L21 · MCP 主要有哪些安全风险？

英文问题：What are the main MCP security risks?

工具投毒：藏在工具描述或结果中的恶意指令。Rug pull：你批准后 server 改变了工具行为。混淆代理与权限过宽：server 以比用户更大的权限行事。Token 透传：把客户端 token 转发给下游 API。以及安装第三方 server 带来的普通供应链风险。缓解：对 server 做白名单并锁定版本，审阅工具描述，每个 server 使用最小权限凭证，不信任未知 server 的注解，高风险工具需要审批，所有工具输出都当作不可信数据。

## L22 · A2A 是什么？什么时候用它而不是 MCP？

英文问题：What is A2A, and when would you use it instead of MCP?

Agent2Agent 协议让独立的 Agent（可能来自不同厂商或组织）通过 Agent Card（能力、端点、认证方式）互相发现，并以带生命周期、消息和产物的任务来委派工作。当你的 Agent 需要一个工具或数据源时用 MCP；当你把工作交给另一个拥有自己推理、工具和策略的 Agent 时用 A2A（例如你的采购 Agent 请求供应商的报价 Agent）。

## L23 · 说出一些 Agent benchmark 以及它们衡量什么。

英文问题：Name agent benchmarks and what each measures

SWE-bench（Verified）：解决真实的 GitHub issue，使隐藏测试通过（编程 Agent）。τ-bench：在领域策略下与模拟用户对话的工具型客服 Agent（零售、航空），提出了衡量可靠性的 pass^k。GAIA：需要浏览、文件和推理的通用助手问题。WebArena / OSWorld：在网站和完整桌面操作系统中操作。BFCL（Berkeley Function Calling Leaderboard）：函数调用准确率，包括并行调用以及何时不该调用。Terminal-Bench：命令行任务。

## L24 · 公开 benchmark 有哪些局限？

英文问题：What are the limits of public benchmarks?

数据污染（测试数据泄露进训练集）、饱和（顶尖分数挤在一起）、依赖脚手架（框架和模型一样重要），以及与你的工具、数据和策略不匹配。用它们来初筛模型，然后用你自己的套件做决定：golden、对抗性和多次重复（如 eval/run_agent_suite.py）。

## L25 · 函数调用的准确率怎么衡量？

英文问题：How is function-calling accuracy measured?

看模型是否选对函数（或正确地不调用），参数是否正确且符合 schema，能否处理多个和并行调用，以及是否会编造不存在的函数。检查方式是与期望调用比对（AST 或结构匹配），或实际执行调用再检查结果。在示例项目的套件中，tools_in_order、tools_not_proposed 以及每步的 invalid_action 状态起同样的作用。

## L26 · 逐项讲讲 OWASP LLM 应用 Top 10，并对应到你的项目。

英文问题：Walk through the OWASP Top 10 for LLM Applications and map it to your project

2025 版：LLM01 提示注入：不可信数据 prompt、verify 节点、审批闸门、注入测试。LLM02 敏感信息泄露：检索前 ACL、日志里不记录 prompt。LLM03 供应链：锁定依赖版本、MCP server 白名单。LLM04 数据与模型投毒：治理生命周期，只检索已发布的文档。LLM05 输出处理不当：schema 校验和 AST 计算器（从不 eval）。LLM06 过度代理：三个工具的白名单、风险分级和人工审批。LLM07 系统提示泄露：prompt 中不放密钥。LLM08 向量与嵌入弱点：向量检索中的租户和 ACL 过滤。LLM09 错误信息：引用和引用准确率。LLM10 无限制消耗：步数、token、成本和时间预算。

## L27 · NIST AI RMF、ISO/IEC 42001 和 MITRE ATLAS 是什么？什么时候提到它们？

英文问题：What are the NIST AI RMF, ISO/IEC 42001 and MITRE ATLAS, and when do you mention them?

NIST AI 风险管理框架把 AI 风险工作组织成四个职能：治理（Govern）、映射（Map）、测量（Measure）、管理（Manage），适合用来搭建治理体系。ISO/IEC 42001 是可认证的 AI 管理体系标准，类似 ISO 27001，但针对 AI。MITRE ATLAS 是针对 AI 系统的攻击战术与技术知识库，类似 ATT&CK，适合做威胁建模和红队规划。讨论企业落地、合规或安全评审时提到它们，并为每一项配上你设计中的具体控制措施。

## L28 · 你会如何给 Agent 做威胁建模？

英文问题：How would you threat-model an agent?

列出资产（数据、凭证、写入能力）、信任边界（用户、模型、工具、检索内容、MCP server、外部系统）和数据流。对每个工具问：一个控制了模型输入的攻击者，最坏能让它做什么？检查致命三要素（私有数据 + 不可信内容 + 对外通道）。控制措施：最小权限工具、身份传递、确定性校验、按风险人工审批、输出过滤、预算以及完整的审计轨迹。然后用对抗性任务做红队测试，并把它们保留为回归测试。

## L29 · 什么是“过度代理”（excessive agency）？如何控制？

英文问题：What is "excessive agency", and how do you control it?

给 Agent 的功能、权限或自主性超出了任务所需。例如只需要“读收件箱”却给了“管理邮件”工具，或为一次只读查询给了数据库管理员凭证。控制：单一用途的窄工具、按用户的最小权限凭证、高影响动作需要审批、限流和预算、审计日志。在示例项目的项目中：三个工具、一个内部写入、审批、幂等和预算。
